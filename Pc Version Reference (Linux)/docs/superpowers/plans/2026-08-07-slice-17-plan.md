# Slice 17 — The status surface: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the Live Status pill becomes the one place that answers "what is
this app doing, and what happened that I need to know about" — via a new
typed `ActivityEvent`, an activity map, and a sticky acknowledgement queue.

**Architecture:** one new backend event type, wired into every long-running
operation as an *additional* yield/broadcast (nothing existing is replaced);
a client-side fold into an `activity` map + sticky queue, additive beside
`byProject`; and a pill rewrite that adds a chevron-toggled detail panel and
sticky-queue handling on top of the existing docked/active states.

**Tech Stack:** Python 3.12 + FastAPI (backend), React 19 + TypeScript
(frontend), pytest, mypy, oxlint.

**Source spec:** `docs/superpowers/specs/2026-08-07-slice-17-status-surface-design.md`

## An open call before Task 1

The spec's §1 ("What is wrong today") describes the pill as three states
derived from one `activeLead`. The code that actually exists
(`web/src/activity.ts` + `web/src/StatusBar.tsx`) is bigger than that: it
already tracks every in-flight **HTTP call** (ambient "Loading"/"Saving",
ranked by `Priority`) and derives `kind`/`label` from `leadActivity()`, not
from a single field. The spec was written without that mechanism in view.

**Nothing in `activity.ts` is a `Priority: "high"` registration from a
socket event today** — despite its own docstring saying that's how a render
should be tracked, no call site does it. So the current pill's "busy" state
already relies entirely on HTTP calls being in flight, which is silent
during a long AI phase between requests. That gap is real and is exactly
what this slice's `ActivityEvent` stream fixes — but it means the new
mechanism and `activity.ts` are two different axes answering two different
questions, and both keep existing:

- `activity.ts` — "is a request in flight right now" (ambient, low-detail,
  HTTP-scoped, unchanged by this slice).
- The new `activity` map + sticky queue — "what long-running operations and
  outcomes has the user not yet acknowledged" (WS-scoped, this slice's
  actual subject).

**Recorded default, in the spirit of Slice 18's corner conflict — REVISED
during implementation:** the plan originally intended to keep `kind`
derived only from `leadActivity(activities)` (the HTTP-call axis) and layer
the sticky queue independently. Building it exposed a real gap: a running
WS-tracked operation with no HTTP call in flight - "a long AI phase between
requests", the exact case this slice exists for - left the pill showing
green/idle the whole time, caught by the SSR structural check in Task 5's
verification (`running-not-docked` failed: the pill docked to an invisible
sliver mid-render). Fixed by folding `activityRows.length > 0` into
`working`/`kind` alongside the HTTP axis, so either one now means "busy" -
see `working`'s own comment in `StatusBar.tsx`. The sticky queue itself
stays the independent axis originally planned: a non-empty queue holds the
pill in its active/expanded (undocked) state regardless of `kind`.

## Global Constraints

Every task's requirements implicitly include all of these.

- **Interpreter is `.venv-build/Scripts/python.exe`.** Tests: `-m pytest tests -q`. Types: `-m mypy`.
- **Capture the CURRENT test count and mypy baseline before Task 1** (run both commands once, record the numbers) — do not assume the counts from Slice 16's plan still hold. Never go below the starting count; add nothing to the mypy baseline.
- **No live API calls in tests, ever.** `tests/conftest.py` forces `AVG_REPLAY_FIXTURES=1`.
- **Nothing below `avg/api/` may print or prompt.**
- **`avg/core/events.py` events are pure Pydantic models — no broadcast logic there.** Broadcasting stays in `avg/api/app.py` / `avg/api/routes_settings.py`, matching every existing event.
- **A terminal `ActivityEvent` (`done`/`failed`/`cancelled`) must be emitted from every code path that can end an operation, including exceptions — a `finally` or `except` that skips it leaves a permanent row in the panel.** This is Slice 16's Transport-bar-stuck-at-100% bug, restated for this feature; §6 of the spec calls it out by name.
- **Never derive `sticky` on the client.** It is a field the emitter sets. A client-side rule like "terminal states are sticky" is explicitly wrong per spec §2.
- **Never use a native form control.** Never add a Google Fonts `@import`.
- **The frontend has no unit tests by convention** — verified by `npm run build`, `npm run lint` (zero warnings), and DOM/computed-style measurement against the dev server.
- **Every motion transition multiplies by `var(--motion-scale)`, is disabled under `prefers-reduced-motion`, and stays visible at `data-motion="none"`.** Slices 13 and 14 each shipped a frozen-element-outside-its-clip bug; do not re-add it here.
- **This slice does not touch `byProject`, `/api/jobs`, or `JobRegistry`.** The `activity` map is additive, per spec §2.
- **Match code by content, not by line number.**
- **Commit once per task**, on local `main`. No push, no PR, no GitHub interaction.

## Task 1: `ActivityEvent` — the typed event itself

**Files:**
- Modify: `avg/core/events.py`
- Create: `tests/core/test_activity_event.py`

**Interfaces:**
- Produces: `class ActivityEvent(BaseModel)` with `type: str = "activity"`, `activity_id: str`, `label: str`, `percent: int | None = None`, `state: Literal["running", "done", "failed", "cancelled"]`, `detail: str | None = None`, `sticky: bool`.

**Why:** Spec §2. One model, reused by every emitter in Tasks 2–3, so the sticky/not-sticky lists in spec §3 have exactly one place they could be wrong.

- [ ] **Step 1: Write the failing test**

```python
"""avg/core/events.py's ActivityEvent - the one event type every
long-running operation emits over /ws/events for the status pill."""

from __future__ import annotations

import pytest
from pydantic import ValidationError

from avg.core.events import ActivityEvent


def test_a_running_event_needs_no_detail_or_percent():
    event = ActivityEvent(activity_id="render:p1", label="Rendering", state="running", sticky=False)
    assert event.type == "activity"
    assert event.percent is None
    assert event.detail is None


def test_state_is_restricted_to_the_four_values():
    with pytest.raises(ValidationError):
        ActivityEvent(activity_id="x", label="x", state="queued", sticky=False)  # type: ignore[arg-type]


def test_sticky_is_required_not_derived():
    with pytest.raises(ValidationError):
        ActivityEvent(activity_id="x", label="x", state="done")  # type: ignore[call-arg]
```

- [ ] **Step 2: Run to verify it fails** — `ModuleNotFoundError`/`ImportError: ActivityEvent`.

- [ ] **Step 3: Add the model to `avg/core/events.py`**, beside `CompositeFinished`, with a docstring naming which emitters use it (Task 2/3's five: pipeline runner, `MediaEngine.render`, Live List refresh, provider probe, model-suggestion run) and stating the sticky rule from spec §2 verbatim (emitter sets it; never derived).

- [ ] **Step 4: Run the test, full suite, types.** Commit: `feat: ActivityEvent, the one event type behind the status panel`.

## Task 2: The pipeline runner and `MediaEngine.render` emit it

**Files:**
- Modify: `avg/pipeline/runner.py`
- Modify: `avg/media/engine.py`
- Modify: `tests/pipeline/test_runner.py`
- Modify: `tests/media/test_engine.py` (or wherever `MediaEngine.render` is covered — confirm the actual path first)

**Interfaces:**
- Consumes: Task 1's `ActivityEvent`.
- Produces: both generators additionally yield `ActivityEvent` at start and at every terminal outcome. `activity_id` is `f"pipeline:{project_id}"` for the runner, `f"render:{project_id}"` for the engine — stable across one operation's whole life, per spec §2.

**Why:** spec §2's sticky list includes "a pipeline or phase error", "a render failure", "a video completed successfully", "an export finished", "a job cancelled" — all of which these two generators already know about, since they already yield `PhaseFailed`/`PipelineCancelled`/`RenderFinished`/`RenderCancelled`/`PipelineFinished`. This task adds one `ActivityEvent` alongside each existing terminal yield, not a parallel state machine.

- [ ] **Step 1: Write the failing tests**

For the runner: a run that reaches `PipelineFinished` also yields exactly one `ActivityEvent` with `state="done", sticky=True`; a run that raises inside a phase (yields `PhaseFailed`) also yields one `ActivityEvent` with `state="failed", sticky=True`; a `PipelineCancelled` run also yields one with `state="cancelled", sticky=True`; the `activity_id` is identical across every `ActivityEvent` yielded in one run.

For the engine: `RenderFinished` pairs with `ActivityEvent(state="done", sticky=True)`; `RenderCancelled` pairs with `ActivityEvent(state="cancelled", sticky=True)`; a `PhaseFailed` from inside render pairs with `ActivityEvent(state="failed", sticky=True)`; a `ProgressEvent` mid-render is accompanied by (or itself followed by) a `running`, `sticky=False` `ActivityEvent` carrying `percent`.

Follow `tests/pipeline/test_runner.py`'s existing harness shape rather than inventing a new one — this is the same exception Slice 16's plan noted for its Tasks 2–3.

- [ ] **Step 2: Run to verify failure.**

- [ ] **Step 3: Wire the runner.** In `avg/pipeline/runner.py`'s `run()`, yield an `ActivityEvent(activity_id=f"pipeline:{project.id}", label="Running pipeline", state="running", sticky=False)` once at the start (mirrors the existing "say it began" comment pattern already in `avg/api/app.py`'s pipeline worker), and yield the matching terminal `ActivityEvent` at each of the three existing terminal yield sites (`PipelineFinished`, `PhaseFailed`, `PipelineCancelled`) — same `activity_id`, `sticky=True` per spec §3.

- [ ] **Step 4: Wire the engine.** Same pattern in `avg/media/engine.py`'s `render()`: a `running` event near the top, terminal events beside `RenderFinished`/`RenderCancelled`/the render-path `PhaseFailed`. Progress ticks get `running, sticky=False, percent=<value>` — cheapest done by converting the existing `ProgressEvent` yield sites to also yield an `ActivityEvent`, not by adding a second loop.

- [ ] **Step 5: Full suite, types, commit.** `feat: pipeline and render emit ActivityEvent`.

## Task 3: Live List refresh, Test Providers, and model-suggestion run emit it

**Files:**
- Modify: `avg/api/routes_settings.py`
- Modify: `tests/api/test_routes_settings.py` (confirm actual filename first)

**Interfaces:**
- Consumes: `request.app.state.manager.broadcast_threadsafe` (same call `avg/api/app.py`'s `_emit` uses — these three operations currently run on background threads with **no** broadcast at all, only pollable state).
- Produces: three new `activity_id`s: `"live-list-refresh"`, `"provider-probe"`, `"live-list-suggest"`.

**Why:** spec §2 says "every long-running operation emits it... the Live List refresh, the provider probe, and the model-suggestion run" and names this the actual test of the design — "a future long-running operation appears in the panel by emitting, with no change to the pill at all." These three are today's proof: none of them touch `/ws/events` at all right now (`refresh_live_list`, `build_model_cache`'s `_sweep`, `suggest_live_list`'s `_run` all just mutate `app.state`/save-to-disk and rely on the client polling `GET /api/live-list`).

Per spec §3, **provider probes where everything passed are not sticky**; a probe that fails on an expired key **is** sticky (it is explicitly named as one of the sticky cases: "a provider or API-key failure: auth, quota, or rate limit"). A Live List refresh is never sticky. The suggestion run's failure path (`app_state.suggest_status = "error"`) is not in either of spec §3's lists by name — reason from the two lists' intent (routine progress vs. something the user needs to see) and record the choice in this task's `Why`, since the drift test in Task 5 will need a decided answer, not an implicit one.

- [ ] **Step 1: Write the failing tests** — for each of the three routes: a `running` `ActivityEvent` is broadcast when the thread starts; a terminal one is broadcast when it ends, on both the success and the exception paths; `sticky` matches the classification above; `activity_id` is stable across an operation's own events. Use the existing `app_state.manager`/broadcast test doubles already in the test file for the pipeline/render routes rather than building new ones.

- [ ] **Step 2: Run to verify failure.**

- [ ] **Step 3: Add a small local `_emit` to each route** (or one shared helper if the three routes already share a module-level one — check first), following the exact pattern already in `avg/api/app.py`'s pipeline worker: `with suppress(Exception): app_state.manager.broadcast_threadsafe(event.model_dump(mode="json"))`. Wrap `_list_everything`, `_sweep`, and `_run` each with a `running` emit before the thread body and a terminal emit in every return/except path (there are multiple early-return error paths in `suggest_live_list`'s `_run` — every one needs its own terminal emit, per the Global Constraint above).

- [ ] **Step 4: Full suite, types, commit.** `feat: Live List refresh, provider probe, and model suggestions report to the status panel`.

## Task 4: The client folds `ActivityEvent` into an activity map and a sticky queue

**Files:**
- Modify: `web/src/useEvents.ts`

**Interfaces:**
- Consumes: the `ActivityEvent` messages Tasks 2–3 now broadcast.
- Produces: `EventsState.activity: Record<string, ActivityEvent>` (mirrors `avg/core/events.py`'s `ActivityEvent`, `kind` left as `string` per the file's own existing convention for forward-compat), and `EventsState.stickyQueue: ActivityEvent[]`, newest first.

**Why:** spec §2–3. This is the client-side half of Task 1's contract.

- [ ] **Step 1: Add the TS interface**, matching `avg/core/events.py`'s `ActivityEvent` field-for-field, added to the existing `EngineEvent` union.

- [ ] **Step 2: Fold into `activity`.** A `running` event writes/overwrites `activity[activity_id]`; a terminal event (`done`/`failed`/`cancelled`) **removes** the entry — spec §2: "A terminal state... removes the entry from `activity`, so a finished operation stops occupying a row." This is a new fold function beside `foldPhases`/`foldByProject`, not folded into either — it is keyed by `activity_id`, not `project_id`, and several of Task 3's emitters have no project at all.

- [ ] **Step 3: Fold into `stickyQueue`, independently.** Per spec §3, this is **client state keyed by event id, not a socket subscription** — every event carrying `sticky: true` is *appended*, regardless of what the fold above did with `activity`. Acknowledgement (Task 5's `x` button) removes the head by `activity_id`. A reconnect must not re-fire acknowledged events — since the queue is plain React state that survives a reconnect (the socket drop only flips `connected`), this falls out for free as long as acknowledgement genuinely mutates the queue rather than being derived from it each render; state this explicitly in the code comment, since it is easy to accidentally re-derive.

- [ ] **Step 4: Build.** `cd web && npm run build` — clean. Commit: `feat: fold ActivityEvent into an activity map and a sticky queue`.

**Files:**

**Interfaces:**
- Consumes: the sticky/not-sticky classification actually implemented across Tasks 2–3.

**Why:** spec §6, verbatim: "Every event in §3's sticky list is emitted with `sticky: true`, and every event in the not-sticky list with `sticky: false`. This must be written **after** Tasks 2–3 exist, not guessed at in Task 1, so it tests real emitter output rather than the model in isolation.

- [ ] **Step 1: Enumerate every emit site added in Tasks 2–3** (grep `ActivityEvent(` across `avg/`) and assert, per site, that its `sticky` literal matches spec §3's two lists:
